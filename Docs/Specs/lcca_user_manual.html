Qu'est-ce que LCCA ?

LCCA est un agent de codage local qui modifie votre code de façon chirurgicale et sécurisée. Contrairement aux éditeurs qui font du chercher-remplacer, LCCA parse l'AST (arbre syntaxique) de vos fichiers Python pour ajouter, modifier ou supprimer des fonctions avec une précision parfaite.

Chaque modification est encapsulée dans une transaction : si quelque chose tourne mal (syntaxe invalide, erreur réseau, crash), les fichiers sont automatiquement restaurés à leur état d'origine.

Format de commande DSL

Nom logique du projet. Sert à contextualiser le sprint log.
Cible
Nom du module ou fichier (sans extension). FileSelector résout le path.
Action
Verbe : Ajoute, Modifie, Supprime, Crée, Corrige, Refactore.
Détails
Signature, description, contraintes — transmis au LLM.

Interface langage naturel

L'interface NL transforme vos instructions en commandes DSL via Qwen2.5-Coder (Ollama), puis les exécute normalement dans le pipeline LCCA. Sans Ollama, un mode heuristique (regex) prend le relais avec une confiance réduite.

⚠ Ollama requis pour les meilleures performances. Sans Ollama, le mode heuristique fonctionne pour les commandes simples mais peut échouer sur les formulations ambiguës.

Confiance et seuil

Le NLParser attribue un score de confiance (0–100%) à chaque intent détecté. En dessous de 40%, la commande est refusée par défaut.

  • OK Confiance ≥ 40% — commande exécutée normalement. Mentionner le fichier cible améliore toujours la confiance.
  • REFUS Confiance < 40% — refusé sans --auto-confirm. Reformulez avec plus de précision (fichier, fonction, action).

Pipeline d'exécution complet

Chaque commande DSL ou NL traverse le même pipeline de 9 étapes. Toutes sont instrumentées (logs, télémétrie).

1
DSLParser — Intent structuré
Parse la commande en objet Intent : projet, cible, sous-cible, action, détails, confiance (0–1). Les commandes NL sont converties en DSL avant cette étape.
2
Spec Layer — Validation architecturale (optionnelle)
Si ADAPTIVE_SPEC_ENABLED=True et complexité ≥ seuil : génère une spec, la valide via 15 règles. Bloque si la spec n'est pas validable après auto-fix. Réutilise les specs existantes depuis lcca_specs.
3
FileSelector — Sélection des fichiers
3 stratégies : correspondance directe nom → fichier, recherche dans l'index AST, fallback sur le dependency graph. Maximum 3 fichiers par transaction (MAX_FILES_PER_TX).
4
MultiFilePlanner — Plan ordonné
Crée un plan d'opérations trié par ordre topologique (dépendances entre fichiers). Valide la cohérence du plan avant exécution.
5
TransactionManager — BEGIN + snapshots
Ouvre une transaction ACID. Prend des snapshots MD5 de chaque fichier cible. Écrit un BEGIN dans le WAL JSONL. Crée les backups .bak.
6
LLMGenerator — Génération code
Appelle Ollama (Qwen2.5-Coder) avec le contexte du fichier. Cache LLM versionné par modèle. Si Ollama indisponible → FallbackGenerator (stub).
7
SmartPatcher — Patch AST via libcst
Applique le code généré dans l'AST du fichier existant. Retourne le code modifié (jamais n'écrit directement). L'écriture est faite par TransactionManager.
8
Validation syntaxe
Vérifie chaque fichier modifié avec compile(). Si une erreur syntaxique est détectée : rollback automatique, restauration des backups .bak.
9
COMMIT — Finalisation
Écrit COMMIT dans le WAL. Re-indexe l'AST du workspace. Met à jour le sprint log dans Docs/Sprints/current-sprint.md.

Gestion des transactions

LCCA implémente un modèle transactionnel ACID via un WAL (Write-Ahead Log) JSONL. Chaque modification est tracée et peut être restaurée.

WAL — Write-Ahead Log

Le WAL est un fichier transactions/wal.jsonl qui trace toutes les opérations en temps réel. Chaque ligne est un objet JSON autonome.

Type d'entréeSignification
BEGINOuverture d'une transaction — snapshot MD5 pris
OP_STARTDébut d'une opération sur un fichier
OP_SUCCESSOpération appliquée avec succès
OP_ERRORErreur sur l'opération — rollback déclenché
COMMITTransaction terminée et commitée
ROLLBACKTransaction annulée, fichiers restaurés

Consulter les transactions

PowerShell
# 10 dernières transactions commitées
python main.py --list-tx

# Sortie :
# ✅ tx_1e1044830819 | 2026-04-18 14:32 | 2 op(s)
# ✅ tx_2363e45c41d4 | 2026-04-18 15:01 | 1 op(s)

Rollback et récupération

En cas d'erreur, LCCA effectue automatiquement un rollback. Les backups .bak sont utilisés pour restaurer les fichiers originaux.

PowerShell — Récupération manuelle
# Détecter et réparer les TX orphelines (crash système, etc.)
python main.py --recover

# Sortie :
# 2 transaction(s) orpheline(s) détectée(s).
# ✅ tx_abc123: committed
# ⏮️  tx_def456: rolled_back

Archivage du WAL

Le WAL peut grossir avec le temps. La commande --clear-wal l'archive et repart sur un WAL vide.

PowerShell
python main.py --clear-wal
# → Demande confirmation
# → Archive vers transactions/wal_archive_20260418.jsonl
✓ Les archives WAL sont conservées indéfiniment dans transactions/. Les backups .bak sont créés par transaction dans transactions/tx_<id>/.

Spec Layer — Validation architecturale

Avant toute modification complexe, la Spec Layer génère et valide une spec technique. Ce mécanisme garantit la cohérence architecturale et prévient les modifications non réfléchies.

ℹ La Spec Layer est active par défaut (ADAPTIVE_SPEC_ENABLED=True). Elle ne s'active que si la complexité estimée dépasse le seuil (SPEC_COMPLEXITY_THRESHOLD=3). Les commandes simples la court-circuitent.

Flux Spec Layer

1
Estimation de complexité
SpecComplexityEstimator analyse l'intent. Score ≥ seuil → spec requise. Score < seuil → pipeline continue directement.
2
Recherche spec existante
Cherche dans lcca_specs une spec réutilisable. Si trouvée et is_usable() → incrément usage_count, pipeline continue.
3
Génération nouvelle spec
DeepReasoningPattern + SpecFormatterPattern (via LLM) génèrent une spec Markdown structurée avec titre, abstract, corps, critères d'acceptation.
4
Validation — 15 règles
SpecValidatorService applique le RULE_REGISTRY (R01–R15). Si violations bloquantes → auto_fix() (max 3 itérations).
5
Stockage ou blocage
Spec valide → stockée dans lcca_specs, pipeline continue. Spec non validable après auto-fix → erreur loggée dans lcca_failures, exécution bloquée.

Désactiver la Spec Layer

Pour les commandes simples ou les tests, vous pouvez désactiver la Spec Layer dans config.py :

config.py
ADAPTIVE_SPEC_ENABLED = False   # désactive la Spec Layer globalement
SPEC_COMPLEXITY_THRESHOLD = 10  # ou monter le seuil
⚠ La Spec Layer requiert Ollama pour générer des specs de qualité. Si Ollama est indisponible, la génération retourne une spec vide qui échoue la validation → exécution bloquée. Désactivez ADAPTIVE_SPEC_ENABLED si Ollama n'est pas disponible.

Règles invariantes

  • ❌ Jamais de modification directe hors workspace\ — safe_path() bloque toute tentative de traversal.
  • ❌ Maximum 3 fichiers par transaction (MAX_FILES_PER_TX). Au-delà, décomposer en plusieurs commandes.
  • ✓ Toujours utiliser --dry-run avant une première modification sur un fichier critique.
  • ✓ Les backups .bak dans transactions/tx_*/ permettent une restauration manuelle si nécessaire.
  • ❌ Spec Layer requiert Ollama. Si Ollama est indisponible, définir ADAPTIVE_SPEC_ENABLED=False.

Résolution de problèmes courants

SymptômeCause probableSolution
"Aucun fichier cible identifié" Nom de module introuvable dans l'index AST Vérifier le nom exact avec --status, ou préciser le chemin complet
"Spec Layer a bloqué l'exécution" Ollama indisponible ou spec non validable Démarrer Ollama, ou définir ADAPTIVE_SPEC_ENABLED=False
"Confiance trop faible" Commande NL ambiguë Mentionner le fichier cible explicitement, ou utiliser --auto-confirm
"Syntaxe invalide après patch" LLM a généré du code syntaxiquement incorrect Rollback auto effectué. Reformuler la commande avec plus de contexte
TX orphelines au démarrage Crash système pendant une transaction python main.py --recover
